## 3. Defect found and fixed (B2-C-SCHEMA correction)

**Defect (verified in the file).** In the pre-fix migration 01, `@b2c_has_reviewer_col`
was probed at ~line 91, BEFORE the guarded `ALTER TABLE ... ADD COLUMN reviewer_user_id`
executed at ~lines 95–100. MySQL user variables are not refreshed by later DDL, so on a
first application the variable stayed `0` after the ADD. The next guard (adding
`fk_exam_attempts_reviewer`, ~lines 105–114) required `@b2c_has_reviewer_col = 1`, so the
FOREIGN KEY was silently skipped on the first run. The schema looked half-applied and
the second run was the first to add the FK.

**Fix.** After the ADD COLUMN block, a fresh probe `@b2c_has_reviewer_col_after` reads
`INFORMATION_SCHEMA.COLUMNS` again (new lines 110–112) and the FK guard uses it (line
118). Idempotency is preserved: a second run sees both the column and the constraint,
so the guards produce `SELECT 1` and add nothing. Forward-only, no DROP/TRUNCATE/
FK_CHECKS, same engine/charset/types.

**Whole-file audit (01).** Every guard was checked for a probe that is computed before
an earlier statement in the same file changes what it probes:

- Step 1 (revisions table) — probes its own table immediately before CREATE; nothing
  earlier creates it. OK.
- Step 2 (attempts table / reviewer column) — probes the table and column immediately
  before the ADD; the ADD is the change being guarded. OK.
- Step 3 (reviewer FK) — was the defect; fixed by the fresh post-ADD probe. The
  `@b2c_has_attempts` probe is unaffected because ADD COLUMN does not change table
  existence, and the FK probe reads the current constraint catalog. OK after fix.
- Step 4 (publications table) — probes its own table immediately before CREATE. OK.

No other guard in 01 has the class of bug.

**Audit of migration 02 (not changed).** Each of the six statements probes exactly the
table it is about to CREATE, and no earlier statement in 02 creates that table. There
is no ADD COLUMN/ADD INDEX/ADD CONSTRAINT guard whose probe could be stale. The same
defect class is therefore absent; migration 02 was left byte-identical.

## 4. Part C — what migration 20261021_02 defines

landed (404 lines). All tables `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
COLLATE=utf8mb4_unicode_ci`; every table has `tenant_id CHAR(36) NOT NULL` + FK to
`tenants(id)`; creation order accounts → journals → journal_lines → reservations →
idempotency_keys → reservation_events so every composite FK target exists first.

|---|---|---|

  trigger is written (the contract does not require them and trigger syntax/privilege
  safety cannot be proven in an authoring batch). The obligation is contractual
