### B.1 `notification-worker.ts` — `toDeliveryAdapter` lost the readiness reason

Before: the bridge returned `{ outcome: 'unavailable', reason: 'adapter-not-ready' }`
whenever `adapter.readiness().ready` was false. After: it reads the readiness
result once and returns `{ outcome: 'unavailable', reason: readiness.reason }`.
Why: `ConfiguredChannelAdapter.readiness()` already carries a bounded, specific
reason (`no-provider-configured`, and a deployer's own reason); replacing it
with a generic label wrote an operator-invisible cause into `last_error` and hid
which configuration was missing. This is the production root cause of failing
test #1. No behaviour change for a ready adapter; no message id is ever invented.

### B.2 `delivery-channels.ts` — `redactPiiText` masked only digit runs

Before: `text.replace(/\d{6,}/g, '••••••')` then whitespace-collapse and
truncation. After: email addresses, `key=value` / `key: value` credentials
(`token|otp|passcode|password|secret|pin|api_key|access_token|refresh_token|
authorization|bearer`), `Bearer <credential>`, double-quoted fragments and 6+
digit runs are all masked, then whitespace-collapse and 200-char truncation. The
mask token is exported as `REDACTION_MASK`. Header comment updated to match.
Why: every adapter reason, provider error, `last_error`, receipt detail and log
line funnels through this one function, and an adapter error such as
`token=abc123 … "Sami progress ok"` survived it verbatim — a token and a message
body in logs. This is the production root cause of failing test #3. Deliberate
constraint kept: a bare keyword followed by a word is *not* masked
(`authorization failed` survives), and single quotes are excluded so ordinary
apostrophes cannot corrupt diagnostics.

### B.3 `tests/m6-notification-worker.test.ts` — fixture applied the fence too late

Before: the recording SQL seam evaluated the `attempts = ?` predicate, *then*
ran the `beforeFinish` probe that simulates a competing claim. After: the probe
runs first, then the predicate. Why: the fixture modelled a store that cannot
enforce the fence — it let a write through after the row had changed. MySQL
evaluates the predicate and the write atomically under one row lock, so a claim
that landed while the dispatcher was inside the adapter *is* visible to the
predicate. This is a **test-fixture defect, not a production defect** (§C.3). No
assertion was relaxed: the test still requires `result.outcome === 'sent'`, one
adapter call, `row.status !== 'sent'`, `delivered_at === null` and a
`state-transition-rejected` log.

Also in this file: one new test
(`the bridge surfaces the adapter readiness reason instead of a generic one`)

### C.2 The three failures — root cause per test

1. **`an adapter with no provider reports unavailable and the row is never marked sent`
   — production bug.** The dispatcher already classified the send correctly
   (`counts.unavailable = 1`, row `pending`, `delivered_at` null, zero receipts);
   only `last_error` said `adapter-not-ready` instead of
   `no-provider-configured`, because `toDeliveryAdapter` discarded
   `readiness().reason`. Fixed in production (B.1). The assertion is a real
   requirement: an operator must see *why* a channel cannot deliver.
2. **`a superseded claim cannot write a terminal state (attempts fence)` —
   test-fixture bug.** The production fence is
   `WHERE id = ? AND status = 'sending' AND attempts = ?` in one statement, with
   the token derived from the claim itself; the store enforces it atomically.
   The recording seam evaluated the predicate against the pre-probe snapshot and
   then applied the competing bump, so the write it should have rejected was
   allowed — a fixture that cannot enforce a fence it is supposed to model.
   Fixed in the fixture (B.3). No production change; no assertion relaxed.
3. **`worker logs carry no email, phone, OTP, token or message body` —
   production bug.** `redactPiiText` masked digit runs only, so
   `token=abc123` and the quoted body `"Sami progress ok"` reached the log (and
   would have reached `last_error` and the receipt detail). Fixed in production
   (B.2). The assertion is the actual security requirement, not a formatting
   preference.

### C.4 Limitations and what I did not do

- **No real send, no provider, no network.** Every provider claim rests on an
  injected recording transport. `unavailable`, `unknown`, `sent`, `bounced` and
  permanent/transient `failed` are proven as *classification*, not as provider
  behaviour.
- **No `unknown` status.** Quarantine is `status='sending'` +
  `last_error='provider-outcome-unknown'` because the outbox ENUM has no member
  and migrations are out of scope. Reconciliation is manual; no poller or
  operator tool exists in this batch.
- **`stop()` may return `drained: false`.** A slow adapter keeps running past
  `drainTimeoutMs`; the worker reports it rather than killing it.
- **Consent window.** A STOP landing between the consent read and the adapter
  call is not observed by that attempt (one adapter call wide). Closing it needs
  a provider idempotency key or a consent version fence in the store — not
  available here (contract §12.7).
- **No DB / Docker / mysqld / listener / network / provider / secret / install /
  migration / Git mutation.** No migration or DDL was authored or executed. No
  TLS or trust-store setting was touched.
- **No full suite** while the other recovery workers are writing (only the three
  focused suites and `tsc -p server/tsconfig.json`).
- **Concurrent writers observed, not touched.** During this run the W4/W6
  recovery workers' files moved on disk (`routes/assignments.ts`,
