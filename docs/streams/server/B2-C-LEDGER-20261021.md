## 4. Contract summary

Canonical file: `docs/contracts/BILLING-LEDGER-INTERNAL-CONTRACT.md`.

- **Tables (6):** `billing_accounts`, `billing_journals`,
  `billing_journal_lines`, `billing_idempotency_keys`, `billing_reservations`,
  `billing_reservation_events`.
- **Identifier/type convention:** `CHAR(36)` IDs, `CHAR(3)` ISO-4217 currency,
  InnoDB/utf8mb4, UTC millisecond timestamps.
- **Money units:** integer minor units only (EGP piaster). `BIGINT UNSIGNED`
  line amounts `> 0`; signed `BIGINT` normal-side balances `>= 0`; per-line /
  per-operation domain bound `10^15`; balances bounded by signed 64-bit
  `9223372036854775807`. Money crosses code boundaries as decimal strings.
- **Account kinds:** `platform_receivable` (debit normal), `platform_cash`
  (debit normal), `merchant_pending` / `merchant_available` /
  `merchant_reserved` / `subscription_credit` / `cash_receipt_clearing`
  (credit normal). One row per `(tenant_id, kind, currency)`.
- **Keys:** account unique `(tenant_id, kind, currency)` and
  `(id, tenant_id)`; journal unique `(tenant_id, reversal_of_journal_id)` and
  `(id, tenant_id)`; line PK `(journal_id, line_no)`; idempotency PK
  `(tenant_id, scope, idempotency_key)` with unique journal/reservation
  targets; reservation unique `(id, tenant_id)` and key/status index;
  reservation event unique `(tenant_id, idempotency_key)` and
  `(reservation_id, event_type)`.
- **Balance/post rules:** normal-side arithmetic; debits must equal credits
  per journal and per currency; 2–100 lines; no cross-currency journal; a
  tenant holds a separate balance per `(kind, currency)`.
- **Structural guards in code:** a journal may not mix `subscription_credit`
  with any merchant wallet kind; may not mix `cash_receipt_clearing` with any
  merchant wallet kind; a cash receipt posts only
  `platform_cash` debit / `cash_receipt_clearing` credit.
- **Append-only:** journals, lines and reservation events are INSERT-only; a
  correction is a reversal journal with swapped sides and
  `reversal_of_journal_id`; one reversal per original journal; accounts and
  reservations change only via CAS transitions, never delete.
- **Lock order:** posting locks affected accounts in ascending `account_id`;
  reservation transitions lock the reservation row first, then accounts in
  ascending `account_id`.

## 5. What a SQL adapter must do

- Use **one connection** for the whole `runAtomic` callback; no pooled
  autocommit between journal, lines, idempotency, balances, reservation and
  event writes.
- Lock every touched account with `SELECT ... FOR UPDATE` in ascending
  `account_id` order; reservation transition locks the reservation row first.
- CAS every balance update:
  `UPDATE ... SET balance_minor=?, version=version+1 WHERE id=? AND tenant_id=?
  AND version=?`; affected rows must be exactly 1 or the transaction aborts.
- Insert the idempotency key under its unique PK; on duplicate re-read and
  compare `payload_hash` (same → replay, different → conflict).
- CAS reservations with
  `WHERE id=? AND tenant_id=? AND version=? AND status='reserved'`; affected
  rows must be 1, including release/consume.
- Assert sufficient `merchant_available` under the account lock before posting
  a reserve.
- Never auto-create accounts; never read `instructor_wallets`,
  `instructor_wallet_transactions` or `services/service-credit.ts` as ledger
  state.
- Honor the 36-character identifier and 10^15 line bounds before SQL.

## 7. Limits and honest non-claims

- The store used here is **in-memory**. It proves domain invariants and the
  transaction-seam behavior, **not** MySQL atomicity, locking, FK enforcement
  or unique-key races. No SQL was executed; no database, Docker or network was
  touched.
- Concurrent same-reservation-key creation can return a typed
  `reservation_key_conflict` rather than a replay; sequential same-key replay
  and same-key/different-payload conflict are proven. A SQL adapter should
  catch the unique-key race and re-read, as the contract says for the
  idempotency table, if it needs concurrent same-key replay.
- The `runAtomic` callback is executed and rollback discards staged writes in
  the test store; this is the seam the future adapter must implement with a
  real connection.
- `tsc --noEmit -p server/tsconfig.json` was run provisionally: **exit 0, no
  errors** in the current dirty tree. Other workers may change that later.
- No production financial API, provider integration, manifest registration,
  route, or frontend bridge was added.
