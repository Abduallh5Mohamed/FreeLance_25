## الدليل والهدف

tenant-self.ts يستعمل createTenantSelfRouter مع dependencies محقونة؛ getOwnedTenant
يحل المؤسسة عبر req.user.tenantId وهوية فعلية وloadActiveTenantAuthority، ثم
يقرأ tenants. /subscription و/billing ليسا عقد profile مستقلًا، وplatform-tenants
يعرض بيانات إدارية خاصة. لا نعيد تسمية كشف إداري كصفحة عامة.
وجود subject_type مثبت في platform-tenants SELECT/INSERT إلى جانب business_name.

قبل: العميل يحتاج هوية مساحة المؤسسة دون الاعتماد على billing DTO أو تخمين
localStorage. بعد المقترح: GET /api/tenants/me/profile يعيد إسقاطًا محدودًا
للمؤسسة التي اختارها الخادم بعد تحقق الصلاحية القائم. لا اختيار tenant من
query/body/header، ولا تمرير ID لمؤسسة أخرى أو fallback لأول membership.

## العقد المقترح

- نفس authenticate وselected-tenant authority المستخدمة أصلًا في tenant-self؛
  لا صلاحية جديدة مشتقة من role محلي، ولا توسيع staff/admin للعضوية القائمة.
- 200 مع Cache-Control:no-store وDTO محصور:
  `{ tenant: { id, business_name, subject_type: string|null, status } }`.
- لا owner_user_id أو الهاتف/البريد أو أعضاء أو رصيد/فوترة/رموز/روابط.
- غياب العضوية/المساحة المسموحة يرجع404 بالنمط الحالي
  `Tenant membership not found`؛ أخطاء authentication الفعلية تبقى401؛
  selectors العميل تخضع لحدود tenant-authority الحالية. حالات الصلاحية
  الفعلية تثبت من المصدر، لا اختراع أدوار أو HTTP classification من العميل.
- GET فقط، لا تغييرات أسماء/شعار/نطاق/فرع أو صلاحية وصول مدفوع.

## مراجعة تحضيرية إضافية — 2026-10-19 القاهرة، سجل081

قراءة مصدر فقط، دون تشغيل اختبار أو خدمة أو تعديل الخادم:

- `server/src/routes/tenant-self.ts` يستورد DB وMinIO وخدمة التجديد عند التحميل؛
  حقن factory وحده لا يمنع آثار import. اختبار `m1-expanded-tenant-admin.test.ts`
  الحالي يحمّل هذه الوحدات فعلًا، لذلك لا يُنسخ كما هو لإثبات شرط عدم قراءة env.
  الاختبار المقترح يجب أن يعزل تلك الأوراق قبل تحميل router، دون قراءة ملفات إعداد
  أو إنشاء عميل خدمة؛ ثم يقود factory الإنتاج وطبقات الصلاحية الفعلية ببيانات محقونة.
- حارس selectors هو `server/src/middleware/tenant-authority-boundary.ts`:
  headers المذكورة ترجع400، وselectors المتداخلة في query/body ترجع400. اختباره
  منفصلًا عن factory ضروري لأن الحارس ليس داخل `createTenantSelfRouter` نفسه.
- `auth.ts` يسمح لمسار `/api/tenants/me` بالمرور عبر استثناء billing-only الحالي.
  profile المقترح لا يغيّر ذلك ولا يمنح محتوى مدفوعًا؛ يبقى فحص العضوية النشطة
  القائم وDTO محدودًا. اختبار billing-only يثبت هذا السلوك القائم، ولا يخترع منعه
  أو يعتبر استثناء المسار استحقاقًا ماليًا أو أهلية دخول لبقية المنتج.
- حقل `subject_type` مثبت في SELECT داخل `platform-tenants.ts`؛ query الحالية في
  `getOwnedTenant` لا تختاره. التنفيذ المقترح يحتاج اختيارًا صريحًا للحقل الموجود
  مع مراجعة أثره على استدعاءات helper الأخرى، دون نشر row كاملة أو تعديل schema.
