# طريقة تشغيل WorkBuddy اليدوية مع ترشيد كريديت Codex

**الحالة:** الإجراء الحاكم ابتداءً من طلب المستخدم المباشر في 2026-10-21.

المقصود بترشيد الكريديت هنا هو **كريديت Codex**: يقرأ Codex أحدث دلائل التغيير
فقط، يعيد استخدام نتائج التحقق الحديثة، يشغل الاختبارات المرتبطة بالتغيير، ولا
يكرر الجرد أو الاختبارات الناجحة من دون تغيير أو سبب مراجعة جديد. لا يقلل ذلك
صرامة مراجعة المصدر والعقود والاختبارات المطلوبة للقبول.

عندما يقول المستخدم: **«اعمل طريقة WorkBuddy اليدوية»** أو يطلب مهمة WorkBuddy
جديدة، يتبع Codex هذا الإجراء:

1. يفحص أحدث حالة حقيقية للمهمتين ومسارات الملكية. إذا كان WorkBuddy ما زال
   يعمل، لا يرسل أو يجهز عاملًا ثانيًا؛ ينتظر المراجعة التالية.
2. بعد توقف/تقرير المهمة السابقة، يراجع Codex الكود الفعلي والـdiff والعقود
   والاختبارات والأنواع. لا يعتمد التقرير أو أعداد الاختبارات وحدها.
3. يجهز Codex مهمة M2 جديدة كبيرة ومتماسكة، مع هدف واضح، قبل/بعد، أثر وحدود
   المنتج، مسارات `allowedPaths` الدقيقة، الاختبارات، وشروط الإتمام. يجب أن تكون
   غير متعارضة مع أي تصحيح نشط لدى OpenCode.
4. يحفظ التسليم الكامل في ملف handoff داخل `docs/streams/client/`، وينشر نسخة
   المهمة الدقيقة في:
   `docs/streams/client/coordination/workbuddy-inbox/`.
5. يرسل Codex للمستخدم في المحادثة:
   - مسار ملف المهمة الكامل.
   - مسار `workbuddy-inbox/current-task.json`.
   - نصًا قصيرًا واحدًا جاهزًا للنسخ واللصق في WorkBuddy.
6. **المستخدم وحده ينسخ النص ويلصقه ويضغط Send في WorkBuddy.** Codex لا يفتح
   WorkBuddy، ولا يكتب في واجهته، ولا يضغط Send، ولا يستدعي
   `request-workbuddy.cjs` لهذه الطريقة.
7. في مراجعات Codex كل 15 دقيقة، يتحقق من claim/checkpoint/report الحقيقي ومن
   المصدر، مع إبقاء حدود توفر الجهاز/التطبيق واضحة. وجود ملف inbox وحده لا يعني
   أن WorkBuddy بدأ.
8. إذا وجد Codex خطأ في تسليم WorkBuddy، ينشئ تصحيحًا محددًا بالمشكلة وإعادة
   الإنتاج والمتوقع/الفعلي والإصلاح واختبار الانحدار، ثم يشغل OpenCode عبر CLI
   للتصحيح. لا يعيد WorkBuddy لنفس التصحيح.
9. Codex يشغل OpenCode عبر CLI عند وجود تصحيح مشروع فقط، ويراجعه حتى القبول.
   الخمول من دون مهمة صحيحة لا يبرر استهلاك نموذج أو اختراع عمل.

## النص الذي يرسله Codex للمستخدم

يملأ Codex القيم بين الأقواس ثم يرسل النص فقط:

```text
افتح واقرأ الملف [ABSOLUTE_HANDOFF_PATH] بالكامل، ثم اقرأ
[ABSOLUTE_CURRENT_TASK_JSON] وملف المهمة المشار إليه داخله وملف
docs/streams/client/coordination/README.md. طالب عبر MCP بالمهمة المحددة فقط
بـworkerId فريد، وتأكد أن allowedPaths مطابقة قبل أي تعديل. نفذ المهمة كاملة
داخل المسارات المحددة، حافظ على كل العمل القائم ومالكيه، وسجل checkpoints فعلية.
استخدم اختبارات محلية آمنة ومحددة ولا تشغل DB أو network أو browser أو services
ولا تطبق migrations ولا تعمل Git/deploy/install. توقف عن كل تعديل وفحص قبل تقرير
MCP النهائي، ثم اكتب تقرير worker مختصرًا. لا تعتمد المهمة ذاتيًا ولا تبدأ مهمة
أخرى.
```

## توزيع الأدوار

- **WorkBuddy:** المهام الجديدة الكبيرة فقط، بعد لصق المستخدم النص يدويًا.
- **OpenCode CLI:** تصحيحات التسليمات السابقة التي أثبتتها مراجعة Codex.
- **Codex:** إعداد التسليمات، إعطاء المستخدم النص والمسارات، المراجعة المستقلة،
  تشغيل OpenCode للتصحيح، والمتابعة كل 15 دقيقة.

هذا الإجراء يلغي فقط إرسال Codex المباشر إلى واجهة WorkBuddy الوارد في198. لا
يغير صلاحيات المنتج أو الملفات أو العامل، ولا يفعّل مؤقتًا للعاملين، ولا يسمح
بتشغيل تلقائي بعد انتهاء المهمة.
