# Tabweb Teachers — الملخص التنفيذي للمنتج الكامل

**القرار الحاكم المحدث:** التسعير تدريجي للمدرس والسنتر؛ فوترة المؤسسة كل 30 يومًا مع حساب مدة فعلية بالثواني وتسوية، لا عمولة على الطلاب؛ محفظة السنتر وحده أو المدرس المستقل؛ خصم الاشتراك من المتاح ومهلة 4 أيام. المرجع [19 — القرارات المعتمدة](19-commercial-registration-wallet-agreement-ar.md)، والموافقة قبل التنفيذ في 18. الوثائق ليست دليل تشغيل.

**شرط التنفيذ الحاكم:** قبل كل دفعة تنفيذ يعرض المنفذ المهام والأثر والاختبارات والاستفسارات في المحادثة، وينتظر قرار المستخدم «نفّذ» أو «متنفّذش» أو تعديلات. لا تكفي موافقة سابقة على مرحلة كاملة. تفاصيل الموافقة ورحلات المستخدم في [18 — الرحلات والموافقة قبل التنفيذ](18-workflows-and-execution-approval-ar.md). لا يبدأ التنفيذ إذا بقي استفسار مؤثر دون حسم.

## القرار

Tabweb Teachers منصة SaaS متعددة المؤسسات تدير حضور المدرس الرقمي بالكامل: المحتوى المسجل والمباشر، التقييم والواجبات، المجموعات والحضور، الطلاب وأولياء الأمور، والعمليات المؤسسية. نطاق المنتج هو **كل الوظائف الواردة في هذا المجلد**. ترتيب M1–M8 يحدد الاعتماد الهندسي والتسلسل فقط؛ لا يحذف وظائف من النطاق.

نبدأ بهندسة أمنية وعزل tenant قبل إضافة إمكانات جديدة. لا تنشر ميزة فوق صلاحيات أو ملكية بيانات غير مثبتة. نستفيد من تطبيق React/Express/MySQL الموجود بعد مطابقة كل مسار ومخطط فعلي؛ لا نعيد كتابة المنصة كاملة افتراضيًا، ولا نعد بإمكانية إعادة استخدام أي جزء قبل الاختبار.

## الجهات والأسطح

1. **Super-Admin:** دورة حياة المؤسسات، الخطط والـfeature flags، قياس الطلاب/الدقائق/التخزين، المحتوى والبلاغات، الدعم، impersonation مؤقت ومدقق، التحليلات والتدقيق وMFA.
2. **Teacher/Center:** الهوية والعلامة والنطاقات والفروع، المناهج والدروس والوسائط والاختبارات والواجبات والدفتر والطلاب والمجموعات والجداول والحضور والموظفين والتواصل والتقارير.
3. **Student:** الاكتشاف والتسجيل والدخول OTP والمحتوى والامتحانات والتسليمات والدرجات والتقدم والشهادة والإشعار والدعم.
4. **Parent:** ربط موثوق بالطالب وقراءة التقدم والحضور والدرجات وإرسال تقارير بموافقة عبر WhatsApp/SMS.

## ترتيب التنفيذ (ليس تقليصًا للنطاق)

| المرحلة | الهدف | بوابة الانتقال |
|---|---|---|
| M1 | Security + tenant core | تحقق auth/RBAC/tenant scope؛ cross-tenant A→B لا يقرأ أو يكتب API/file/video/job؛ لا أسرار افتراضية أو عمليات schema مدمرة وقت التشغيل |
| M2 | Teacher/student core | رحلة صفحة مدرس ← تسجيل/انضمام ← مقرر/درس/ملف ← حالة اشتراك الطالب وتقدم |
| M3 | حماية الفيديو | DRM، watermark جزئي، جلسة/جهاز متزامن، تنزيل مسموح بقرار صريح |
| M4 | التقييم والواجبات | question bank، اختبارات مؤقتة، MCQ آلي، تصحيح يدوي، واجبات ودفتر درجات وتقارير |
| M5 | المجموعات والحضور والحي | مجموعات وجداول وحضور يدوي/آلي وحصص حية مدمجة وتسجيل في المكتبة |
| M6 | ولي الأمر والإشعارات | تحقق صلة الولي، سياسة بيانات، تقارير وقنوات opt-in وإلغاء الاشتراك |
| M7 | إدارة المنصة | دورة المؤسسات والخطط والقياس والمراجعة والدعم وimpersonation والتدقيق وMFA والتحليلات |
| M8 | صقل شامل | RTL/إنجليزية، سهولة الوصول، الأداء، البحث، الرصد، النسخ والاسترجاع، التصدير لكل tenant |

المراحل متتابعة لأسباب أمنية واعتمادية. لا تمثل تاريخ إطلاق أو قائمة وظائف مستثناة. لا يبدأ M2 قبل اجتياز اختبارات M1.

## قواعد أساسية

- المدرس/المركز tenant؛ المؤسسة قد تضم فروعًا وعدة مدرسين وموظفين بأدوار دقيقة. الطالب قد يرتبط بأكثر من مؤسسة بعلاقات enrollment منفصلة.
- اشتراك المدرس/السنتر ذاتي عبر بوابة الدفع مع عروض خاصة؛ احتساب بعدد تسجيلات الطلاب عند المدرسين. التحصيل ومحفظة المؤسسة والسحب وفق دفتر مالي ومزود معتمد؛ التفاصيل في 19.
- أسعار المزودين وسلوك API والعقود المتغيرة موسومة **تحتاج تحققًا** قبل الاعتماد، ولا يوجد سعر مستنتج من ملفات الاقتصاديات القديمة.
- عربي RTL هو الافتراضي، الإنجليزية لغة كاملة، وواجهات الطالب والولي mobile-first.
- لا تعمل محاكاة أو وثيقة كأنها دليل تنفيذ: كل حالة تسجل «منفذ/جزئي/غير منفذ/غير متحقق» وترتبط باختبار أو عرض تشغيل.

## أول عشر خطوات هندسية

1. جرد production schema/routes/deployment وحفظ snapshot قابل للاستعادة ومقارنة migrations الفعلية.
2. إيقاف التسجيل الذي يعيّن role ذاتيًا، وتدوير الأسرار المكشوفة، وإزالة fallback secrets.
3. تحديد identity/tenant/membership ومصدر tenant الموثوق وعقود صلاحيات موحدة.
4. إغلاق runtime DDL والمسارات الهدامة وhard-delete اليتيم، وتثبيت migration ledger.
5. عزل API وSocket.IO والملفات والفيديو والطوابير بمبدأ deny-by-default.
6. اختبارات A→B للقراءة والكتابة والتصدير وmedia/jobs، وإثباتها قبل M2.
7. إنشاء/ترحيل tenant/member والمفاتيح المركبة والبيانات الغامضة إلى قائمة مراجعة.
8. تطبيق واجهة repository مشتركة للـtenant ومراجعة كل route قبل السماح.
9. تشغيل teacher/student core بعد بوابة M1 مع تسجيل تدقيق وobservability.
10. تنفيذ backlog حسب `17-full-feature-backlog.md` مع اختبار وcommit لكل milestone.
