# BUILD-46 — تشغيل رحلة الرجوع بعد الغياب كاملة على الديمو

دفعة J07 متكاملة: أدلة حضور وتقدم، اختيار ومراجعة المدرس، حفظ متزامن وإيصال، قراءة الطالب، تغير الأهلية وسحب الخطة، وتجربة انقطاع الرد وإعادة تحميل Chrome. الديمو المصطنع فقط؛ لا قبول إنتاجي أو قياس أثر تربوي.

## النتيجة والتغييرات

- `CourseReturnPlan.tsx`: ملخص ظاهر للحاضر والغائب والمتأخر وبعذر وغير المسجل، محسوب من نفس قائمة الأدلة المثبتة. التفاصيل ما زالت متاحة؛ لا مساواة بين عدم التسجيل والغياب ولا تشخيص تلقائي.
- `course-return-plan.ts`: عند تأكيد الخادم للحفظ وفشل تنظيف علامة الاسترجاع، يبقى الإيصال ظاهرًا وتُمنع الكتابة وتغيير الأدلة. GET لنفس العملية يعيد محاولة التسوية. فشل GET أو انتهاء مهلة الاسترجاع لا يمحو الحفظ المؤكد؛ التنظيف الناجح يرفع القفل. لا إعادة POST أو مفتاح جديد تلقائيًا.
- `saved-return-plans.test.ts`: يغطي رفض تخزين العلامة قبل POST، وفشل تنظيفها بعد الحفظ، ومنع save/withdraw/load أثناء التسوية، وفشل GET مع إبقاء الإيصال، ثم نجاح GET والتنظيف وفشل تحديث الأدلة دون تحويله إلى فشل كتابة.
- استُخدمت المسارات والمحركات المركبة القائمة دون نسخ محرك للحضور أو التقدم أو التسجيل أو التقييم. لم تتغير سياسات الوصول أو الماليّات أو ملفات WorkBuddy المحجوزة.

## التشغيل الفعلي

قاعدة `tabweb_demo_20261107162429` فقط. `output/activate-demo-return-plan.cjs` يثبت loopback واسم القاعدة المطابق للـlocator، ويأخذ snapshot خاصة محدودة لكل الجداول إلى `LocalDemo/20261107-182429/before-build46-return-plan.json` قبل DDL. لم تُطبع بيانات حسابات أو إعدادات خاصة.

المطبق بالضبط:

1. من `20261018_11_schedules_attendance_records.sql`: قسم إنشاء `schedule_sessions` و`attendance_records` المحروس فقط، من `SET @has_sessions =` إلى ما قبل قسم Foreign keys، مع `SET @m5_db = DATABASE()`. **ليس** تفعيلًا لـschedule_series أو الـFKs المنفصلة أو مولد مواعيد دوري أو مسار تسجيل حضور. الجداول تحوي الفهارس والـunique guards المضمنة في CREATE.
2. `20261107_01_course_return_plans.sql` كاملًا: head/revisions/operations، مع FK المراجعة إلى الرأس وفهرس صفحة الطالب.

`output/build46-demo-migration-journal.json` يسجل hash وحدود العبارات؛ 11 و3 عبارة اكتملت. فحص `savedReturnSchema` الأصلي على القاعدة أعاد true. DDL ليس قابلًا لـrollback ذري؛ الاستئناف يتبع journal، ولا تعميم لهذه الأداة على قاعدة أخرى.

ست جلسات مصطنعة خاصة بالمجموعة الحالية: أربع مؤهلة لإثبات الحالات الأربع، وواحدة ملغاة وأخرى بجمهور مختلف لاستبعادهما. سجلات الحضور أنشئت بـfixture SQL معلنة، وليست دليل تشغيل واجهة الحضور أو واقعة تعليمية حقيقية. بيانات نوفمبر 2026 داخل مقرر الديمو ذي الاسم «رحلة الموسم 2029» بيانات اختبار سياسات فقط؛ لا تُعرض كتاريخ أكاديمي واقعي.

الواجهة http://localhost:8081 والخلفية 3001، PID **23012 / 2292** كما في BUILD-45؛ لا حاجة لإعادة الخادم، إذ تغييرات المنتج بالواجهة وDDL الديمو فقط. لا مزود أو عامل أو جدول آلي فُعل. بيانات الدخول الخاصة الست كما هي، ولم تُنشأ كلمة مرور جديدة.

## أدلة MySQL/HTTP

`output/verify-demo-return-plan.cjs`، وتسعة فحوص ناجحة في `output/build46-live-results.json`:

- المالك يقرأ القائمة والأدلة مع no-store؛ الحاضر والغائب وبعذر وغير المسجل منفصلة، والملغى والجمهور الآخر مستبعدان.
- تغيير الحضور بعد المعاينة يرفض المراجعة القديمة دون كتابة خطة.
- عمليتا حفظ متزامنتان بالإصدار المتوقع نفسه تعطيان 201/409؛ نسخة وإيصال واحدان. إعادة العملية نفسها وGET لا يكتبان مرة أخرى.
- الطالب المختار يقرأ خطوتين مع مدة معروفة وأخرى مجهولة، دون حضور أو معرف معلم أو مراجعة أو URL في DTO.
- قيد طالب آخر لا يرى الخطة، والطالب لا يستعمل مسار المالك، وselector هوية إضافي مرفوض.
- تغير موعد الدرس أو شرطه السابق يجعل الخطوة `{position,available:false}` فقط، بلا عنوان أو معرف أو مدة مخفية.
- سحب نشر المقرر يخفي الخطة في القراءة التالية؛ الخطة لا توسع النشر.
- المالك يسحب الخطة حتى بعد تعطيل قيد الطالب؛ إيصال الحفظ السابق يظل قابلاً للاسترجاع، وإعادة تفعيل القيد لا تعيد نسخة مسحوبة.
- المراجعة والحفظ والقراءة والسحب لا تنشئ إكمال درس؛ سجل التقدم القديم لا يُدمج بالجديد.
