# BUILD-58 — تشغيل السنتر وفريق مستقل الصلاحيات

8 نوفمبر 2026. تنفيذ المهمة الكبيرة2 محليًا ضمن عقد وافق عليه المالك أثناء
التنفيذ: حساب مستقل لكل موظف، مرتبط بالمؤسسة وفروع موارد مختارة، بصلاحيات
تشغيل محددة، دون مالية أو إدارة منصة. هذا سجل تنفيذ واختبار، وليس قبولًا
ذاتيًا أو إنتاجيًا. [عقد الخادم](../streams/server/J01-CENTER-TEAM.md)،
[عقد الواجهة](../streams/client/J01-CENTER-TEAM.md).

## ما يستطيع المستخدم فعله الآن

المالك يدخل `/instructor` ثم «مركز تشغيل السنتر»: يراجع مجموعاته ومقرراتها
وفروعها وأهلية إعدادها، ويفتح إعداد المجموعة الموجود. يفتح «إدارة فريق السنتر»
لينشئ حسابًا مستقلًا، ويختار فروعًا وصلاحيات صريحة، ثم يعدّل الوصول أو يوقفه
أو يعيد تفعيله أو يضبط كلمة مرور جديدة مع إلغاء الجلسة القديمة.

الموظف يدخل بحسابه إلى `/center-work`، ويختار عضوية عمله، ثم المجموعة والحصة
الفعلية المسموحتين. يقرأ قائمة الحضور المؤهلة ويستخدم محرك الحضور الأصلي
للتسجيل/التصحيح. عدم التسجيل لا يُعرض كغياب. بيانات أخرى أو فرع آخر أو معرف
موظف آخر لا تمنحه وصولًا. لا حساب مالك مشترك ولا صلاحيات مالية افتراضية.

المالك ينشئ طلب تشغيل داخليًا، ويختار المسؤول والفرع وموعد متابعة اختياريًا.
الموظف يرى «المسند لي» ويبدأ المتابعة ثم يؤكد الإنجاز. النقل يتطلب موظفًا نشطًا
له الفرع والصلاحية، وإصدارًا حاليًا؛ يفقد المسؤول السابق الوصول بعد النقل.
التأخير مبني على موعد صريح، دون رسائل أو تصعيد تلقائي.

طلبات الفريق هنا ليست طلبات الطلاب إلى السنتر ولا تفويض تذاكر دعم المنصة.
دعم المنصة الشخصي ومسؤولوه الحاليون يظلون بعقدهم؛ سياقات استقبال الطلاب
والربط بهوياتهم تحتاج امتدادًا مستقلًا. تسليم موظف بديل بشريًا وقياس وقته
والحمل والأجهزة ليست مثبتة بهذه الدفعة وتنتقل لبوابات المهمة5.

## حدود الهوية والتزامن

- `users.center_account=1` حد دائم تقرؤه المصادقة الأصلية. حساب الموظف role=staff
  لكنه لا يحصل على عضوية تدريس أو أدوار إدارة منصة أو عضويات فروع عامة.
  JWT/page/tenant selectors لا تتجاوز الحد. غياب عمود الحد يفشل مغلقًا؛ لا
  fallback يزيل فصل الحسابات عند نقص المخطط.
- الصلاحيات فقط `groups.read` و`attendance.mark` و`tasks.manage`.
  الحضور يتطلب قراءة المجموعات. الفروع هي `branches` الخاصة بموارد المجموعات؛
  `tenant_branches` بيانات إعدادات مستقلة لا تطابق بالاسم.
- المصادقة الحية ونسخة الجلسة والمالك/عضوية الموظف والفرع تُثبت من الخادم.
  التعديل/الإيقاف/ضبط المرور ترفع token_version. الإيقاف يمنع مساحة العمل؛ لا
  ندعي منع كل تسجيل دخول شخصي لاحق أو التحقق من ملكية الهاتف عبر OTP.
- المحرك الأصلي للحضور يستقبل delegation في المسار الضيق فقط، قبل اختصار
  المالك/منشئ الحصة وداخل المعاملة. لا إعادة كتابة لمحرك التقييم أو الحضور.
- إنشاء الحساب والتعديل والطلب والتدقيق والإيصال في معاملة واحدة. فشل commit
  غير محسوم، لا نجاح مفترض ولا إعادة عمياء، ويُتلف الاتصال غير الآمن.
  التدقيق ذري لكنه غير مختوم.
- مفتاح UUID واحد لكل كتابة، fingerprint بلا كلمة مرور، وإيصال تاريخي مرتبط
  بالفاعل والمؤسسة. سحب الفرع/المهمة يمنع إعادة التشغيل أو قراءة الإيصال
  المحتوي على مورد لم يعد مخولًا. إعادة مفتاح الإنشاء لا تعيد ضبط كلمة المرور.
- الواجهة تحفظ UUID فقط قبل POST وتمنع الكتابة الأخرى عند فقد الرد. reload
  ثم GET يسترجع النتيجة دون POST ثان. غياب الإيصال لا يعني عدم الحفظ؛ الإغلاق
  الصريح على الخادم ينشئ tombstone يمنع كتابة متأخرة، أو يعيد المحفوظ أصلًا.
  لا مسح للتاريخ أو تعويض تلقائي. فقد السلطة قد يبقي العلامة مقفولة.
- مهلة25ثانية لكامل الطلب، وحماية تبدل principal واختيار المجموعة وتأخر
  النتائج. عرض بيانات الموظف يختفي بعد60ثانية/مغادرة الصفحة أو عودة التركيز،
  ويتطلب إعادة التحقق؛ ليس وعدًا بسحب فوري دون اتصال. الحفظ المؤكد لا يتحول
  إلى فشل كتابة عند فشل تحديث القائمة.

## عيب الفروع الذي ظهر أثناء التشغيل وإصلاحه

إنشاء فرع موارد عبر المسار القديم كتب الفرع ثم فشل التدقيق بسبب غياب
`branch_audit_log` على الديمو:500 بعد حفظ فعلي. لم نكرر الإنشاء عميانيًا؛
احتفظنا بالفرع المصطنع واستعدنا معرفه بقراءة مباشرة. لا audit backfill مختلق.

الخمسة مسارات المعدلة للفروع أصبحت تستخدم `audited-branch-write.ts` ومعاملة
واحدة. قبل إنشاء جدول التدقيق، اختبار فعلي بعد الإصلاح أعاد500 مع **صفر فروع
جديدة**. ثم طُبقت جملة CREATE الخاصة بالجدول فقط من migration الموارد الموجودة،
بعد snapshot خاص وعلى الديمو وحده. إنشاء فرع جديد بعدها حفظ audit واحدًا.
اختبار SQL rollback-only أثبت رجوع الإصدار عند خطأ التدقيق وحفظ الاثنين معًا
داخل المعاملة الناجحة ثم rollback خارجي بصفر آثار اختبار باقية.
