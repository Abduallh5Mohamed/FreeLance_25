# BUILD-39 — صفحة الأسرة وملخص الحضور والأجندة

**7 نوفمبر 2026** — دفعة متكاملة محليًا من J06: خادم ومصدر بيانات وواجهة فعلية وتنقل وصلاحيات واختبارات. التنفيذ المباشر بواسطة Codex بتفويض المالك؛ OpenCode لم يُشغل والجدولة بقيت Disabled. المرجع [الخطة 22](../22-business-strategy-integration-ar.md)، والحالة والباقي في [قائمة التنفيذ](BUSINESS-EXECUTION-QUEUE.md).

## النتيجة للمستخدم

صفحة **`/family` — متابعة الأسرة** متاحة من قوائم التنقل الحالية. تعرض روابط الأبناء التي يملكها المستخدم المسجل بالفعل، ويختار ولي الأمر رابطًا نشطًا صراحة. لا يُفتح طفل تلقائيًا ولا يُجمع محتوى المؤسسات. بعد إصدار جلسة مشاهدة مخولة لهذا الرابط، تظهر معلومات ابن واحد فقط:

- اسم الابن والمجموعة والمقرر الحاليان عند توفر صلاحية المجموعة.
- حضور آخر سبعة أيام: حاضر ومتأخر وغياب مسجل وبعذر ولم يسجل، كل منها منفصل.
- تفاصيل الحصص المنتهية كمصدر اختياري للملخص؛ عدم التسجيل ليس غيابًا، وبعذر لا ينتج تصنيف تقصير.
- أجندة حصص المجموعة الحالية في الأيام السبعة القادمة، مع الأوقات بتوقيت القاهرة.
- خطوة متابعة واحدة من قواعد معلنة: مساندة عند غياب مسجل، أو تأكيد الحضور غير المسجل، أو الاستعداد للحصة القادمة، أو مراجعة المجموعة مع المدرس. لا تشخيص ولا لوم ولا ترتيب للأبناء.
- وقت آخر تحقق، وتوضيح أن القراءة ليست إشعارًا أو متابعة لحظية، وأن الدرجات غير معروضة دون إثبات نشر للأسرة.

التنقل بين الأبناء يخفي الملخص السابق قبل التحميل. فشل التحديث لا يترك بيانات قديمة على أنها محدثة. تبديل الجلسة أو المساحة يخفي البيانات ويلغي الطلبات القديمة. تُخفى القراءة بعد حد عرض أقصاه دقيقة أو انتهاء التوكن أيهما أقرب، وكذلك عند الخلفية/التركيز، ويلزم تحديث صريح لإعادة التحقق.

هذه الرحلة تستخدم **روابط موثقة موجودة مسبقًا**؛ لا تنشئ حساب ولي أمر أو رابطًا ضمنيًا. إذا لم يوجد رابط نشط، تعرض ذلك بصراحة. تفعيل قناة OTP وإنشاء أول رابط وحساب مناسب لولي أمر بلا حساب طالب ما زال عملًا منفصلًا. قائمة الروابط القائمة محدودة بأحدث 200؛ عند امتلائها تظهر ملاحظة أنها قد لا تشمل التاريخ كله.

## المعمارية وإثبات الصلاحية

المسار الجديد الفعلي `GET /api/parent/family-summary` مركب داخل router ولي الأمر الموجود فعلًا قبل middleware JWT العامة. لم يُعدّل `server/src/index.ts` أو مسارات WorkBuddy المحجوزة. يعاد استخدام خدمة `parent-links` والتحقق الحقيقي من توكن المشاهدة المخزن والرابط والقيد، دون اختراع دور parent أو نظام ربط ثانٍ.

التدفق: اكتشاف روابط المستخدم عبر `GET /api/parent-links`، ثم طلب صريح `POST /api/parent-links/:id/session`، ثم قراءة الملخص بتوكن المشاهدة الخاص فقط. الطلب الأخير لا يحمل JWT المستخدم أو محدد مساحة طالب، ولا يضع التوكن في URL أو التخزين أو حالة الواجهة أو السجلات. لا توجد إعادة إصدار تلقائية في الخلفية. إصدار الجلسة نفسه يستعمل كتابة التوكن الموجودة أصلًا، وليس إيصال إرسال أو نجاحًا مصطنعًا.

قبل جمع البيانات وبعده، يتحقق الخادم من التوكن والرابط الفعلي، مع اشتراط حالة active صريحة وعدم السحب. يعيد قراءة الطالب والمالك في جدول users، ونشاط الحسابين وتعليقهما، والمؤسسة ونشاطها، وحالة القيد ومجاله الزمني. إتاحة المجموعة تحتاج تعيين مقرر نشطًا ومقررًا تابعًا للمؤسسة نفسها ومجموعة بنطاق فرع صالح. أي تبدل في سياق الطالب بعد الجمع يرفض الرد كله. لا يعتمد الخادم على أرقام في الواجهة لاختيار الابن.

مسارات الربط الحالية أصبحت تشترط جلسة شخصية مباشرة من users: هوية staff القديمة وجلسة الانتحال والحساب billing-only ترفض قبل قراءة الروابط أو إصدار جلسة. هذا يمنع تصادم نطاق معرف موظف قديم مع مستخدم ولي أمر. لم تُضف سلطة موظف جديدة.

المصدر محدود بحصص **المجموعة الحالية** فقط: المنتهية خلال الأسبوع السابق، والقادمة خلال الأسبوع التالي، داخل مدة القيد. لا يتضمن هذا تاريخ انتقالات المجموعات أو حصص المؤسسة والفرع العامة. يُستعلم عن 101 صف لكل نافذة؛ وجود أكثر من 100 يرفض الصفحة كاملة بدل حساب ملخص مبتور. التكرار أو تاريخ غير صالح أو حالة حضور غير معروفة يرفض القراءة أيضًا.

تُفحص أعمدة المخطط الفعلي للجداول القائمة، وفهرس مواعيد يبدأ بـ`tenant_id,group_id,starts_at` وقيد حضور فريد دقيق `session_id,student_id`. غيابها ينتج unavailable دون DDL. لا توجد migration جديدة في هذه الدفعة. التحقق لا يثبت أداء الاستعلام؛ قبول EXPLAIN والحمل الفعلي ما زال منفصلًا.

كل ردود عائلة المسارات تحمل no-store، ومسار الملخص يحمل Vary: Authorization. الاستعلامات محددة الأعمدة ومربوطة بمعاملات SQL. الرد لا يحتوي أرقام اتصال أو معرف ولي الأمر أو القيد أو المستخدم أو مفاتيح إجابات أو ملاحظات أو أبناء آخرين. أخطاء الملخص لا تسجل SQL أو بيانات الطفل. القراءة عبر استعلامات حالية منفصلة وليست لقطة نشر ذرية ولا اشتراكًا لحظيًا في السحب.

## تصحيح مهم في المسار القديم للدرجات

قراءة المصدر كشفت أن `gradebook_scores` لا يوفر في العقد المفحوص إثبات نشر درجة للأسرة. المسار القديم `/api/parent/grades` كان يستدعي تجميع الدرجات المسجلة دون هذا الإثبات.

أصبح المسار، بعد المصادقة، يرجع **503 `PARENT_GRADE_PUBLICATION_UNCONFIGURED` دون استدعاء مخزن الدرجات**. هذا تغيير توافق مقصود لحماية الدرجات غير المنشورة، وليس ادعاءً بأن الدرجات غير موجودة. اختباره يزرع درجة ثم يثبت عدم قراءتها أو إعادتها. المخزن القديم المُصدّر باقٍ لاختباراته التاريخية لكنه غير مستدعى من handler المركب. إعادة عرض الدرجات تحتاج عقد نشر ومصدرًا واضحين؛ لم نفترض أن انتهاء التصحيح أو مجرد التسجيل يعني النشر.

## الحدود والباقي

لم تُلمس قاعدة حية أو migrations أو مزود أو OTP فعلي أو نشر أو حزم أو أسرار أو حساب/نموذج بديل. فحص المعلومات من ملفات المصدر واختبارات SQL مبرمجة؛ ليس تجربة عزل MySQL أو EXPLAIN أو حمل أو أجهزة أو متصفح فعلي أو إثبات فهم الأسرة للرسالة. لا تدعي الاختبارات أن المخطط الموروث موجود فعليًا.

تظل J06 جزئية: إنشاء أول رابط وحساب ولي الأمر، وعقد نشر الدرجات والتقدم، ومعلومات/تواتر/تفضيلات ووقت هادئ، وسياسة تجميع الأبناء والمؤسسات وقنوات الإرسال والموافقات والانسحاب والتكلفة والقياس الميداني لم تُستكمل. لا ربط لخطط J07 الخاصة بالمدرس ولا خلط سجلي التقدم.
