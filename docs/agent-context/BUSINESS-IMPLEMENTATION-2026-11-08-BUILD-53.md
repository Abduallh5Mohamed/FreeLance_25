# BUILD-53 — مخطط الربط واختبار MySQL وflag تأجيل الأونلاين

أُنجزت خطوة مخطط الربط وSQL الفعلي على الديمو المعزول، وكُشف وأُصلح عيب انتهاء الدعوة بسبب توقيت اتصال MySQL. أثناء العمل قرر المالك **تأجيل SMS/واتساب إلى حين الاشتراك، وإبقاء التشغيل وراء flag**. نُفذ القرار: ربط الأونلاين مؤجّل ومغلق افتراضيًا من الخادم، والواجهة تُظهر ذلك. لا ننتظر اختيار مزوّد كي نواصل بقية الخطة.

## نتيجة المنتج والـflag

`STUDENT_ACCOUNT_LINK_ENABLED=false` هو الوضع الافتراضي أيضًا عند غياب المتغير. القيمة النصية `true` وحدها تفتح بوابة الرحلة؛ `1` وTRUE وyes وأي قيمة أخرى لا تفعلها. لم نغير إعدادًا خاصًا أو سرًا أو مزوّدًا في البيئة، ولا توجد واجهة عميل أو query/body/header تستطيع تشغيلها.

- يُرفض إرسال طلب ربط جديد ومعاينة/موافقة المالك وقراءة قوائم الاختيار التشغيلية عند التأجيل، برمز409 و`ACCOUNT_LINK_DEFERRED`، قبل طلب اتصال أو استهلاك دليل OTP.
- `/api/student-enrollment/account-link-capabilities` قراءة عامة ثابتة تعرض حالة feature فقط، بلا هوية أو مؤسسة أو جهات اتصال أو طلبات. لا تحتاج جدول الربط ولا حساب دخول. العميل يقرأها دون credentials أو bearer. `/api/tenants/me/catalog/account-link/capabilities` تثبت المالك الحالي داخل معاملتها، دون اشتراط مخطط الربط لعرض التأجيل.
- الرد `{state:'deferred'}`، أو `{state:'verification_required'}` إذا فُتحت البوابة. الحالة الثانية **ليست جاهزية مزوّد أو إثبات تحقق**. كل قواعد OTP الحالية تظل لازمة، والتوصيل القائم ما زال delivery:null.
- لا تعرض واجهة المالك أو الطالب حقول وإجراءات ربط جديدة وهي مؤجلة؛ تظهر «ربط الأونلاين مؤجّل حاليًا». المجهول لا يُوجَّه لتسجيل الدخول لأجل ميزة مؤجلة، ولا تُنشأ له علامة استرجاع زائفة.
- تبقى قراءة الإيصالات وحالة الطلب القديم وسحب موافقته قبل اكتمال الربط متاحة ضمن سلطتها ومخططها، حتى عند التأجيل. عند نتيجة POST مجهولة يُستخدم GET، لا إعادة POST؛ الـflag لا يلغي إيصال عملية سابقة. رسائل إرسال الطلب صارت تصفه كإيصال تاريخي بدل وصفه بانتظار حالي ربما تغير.
- إذا كانت قراءة الإتاحة مجهولة/بطيئة/غير صالحة لا تظهر إجراءات جديدة. حدود الجلسة والمهلة والتخلص من المكون تحجب الردود القديمة. فتح flag مستقبلاً لا يستبدل التحقق أو يربط طالبًا أو يعطي مقررًا تلقائيًا.

التنفيذ في `server/src/routes/student-account-link.ts` و`src/features/enrollment/account-link.ts` و`AccountLinkPanels.tsx`. لا تغيير لملفات تركيب index أو WorkBuddy المحجوزة، ولا تعديل لاستيراد M2-16 أو توسيع DTO الطالب/المقررات.

## إصلاح التوقيت الذي أثبته MySQL

دعوة SQL بعمر ساعة رُفضت في الاختبار الأول كمنتهية رغم بقائها حية في DB. DATETIME المكتوب بـUTC_TIMESTAMP كان يُقرأ عبر تحويل Date بتوقيت الاتصال؛ الإعداد القائم في `server/src/db.ts` هو+02:00، وليس سببًا لتغيير توقيت كل النظام ضمن هذه الدفعة.

أُصلح المسار محليًا:

1. الدعوة وحالة الطلب تقرآن علم `expires_live` المحسوب بـ`expires_at > UTC_TIMESTAMP()`، بدل `new Date(...)/Date.now()` على DATETIME المُحوّل.
2. إدخال الطلب صار INSERT…SELECT يأخذ الأصغر من تاريخ الدعوة وUTC+24h داخل SQL نفسه، دون تمرير Date من JavaScript كحد زمني.
3. معاينة المالك تربط بصمتها بـexpires_epoch من TIMESTAMPDIFF ثابت، دون إدخال تحويل توقيت driver في دليل المراجعة.
4. صلاحية مجهولة أو منتهية تفشل مغلقًا؛ انتهاء الدعوة نفسها يظهر كexpired لطلب pending. لا تغيير لسياسة24h أو توقيت قاعدة البيانات/المجمع العام أو محرك OTP العام.

اختبار MySQL يثبت أن المهلة موجبة وأقصاها ساعة وتساوي حد الدعوة، ثم يحولها داخل المعاملة إلى وقت منتهٍ ويثبت expired ويعيدها. اختبارات الوحدة تثبت رفض علم صلاحية غائب أو منتهٍ، دون fallback إلى Date.

## ثمانية فحوص MySQL فعلية، دون بيانات تحقق باقية

`output/verify-build53-account-link-mysql.cjs` يشغّل **مصانع Router الأصلية وSQL الفعلي على MySQL8.0.44**، داخل معاملة خارجية تُلغى بالكامل. الـprincipal محقون للاختبار، ومفتاح HMAC مؤقت في الذاكرة، وتوصيل OTP عبارة عن adapter اختبار في الذاكرة. الرمز لا يُطبع ولا يُحفظ في ملف. الأصل IdentityOtpService يصدر ويتحقق من هذا الرمز داخل المعاملة؛ لم نكتب consumed_at يدويًا لتظاهر بتحقق فعلي.

كل begin للـroute يقابله SAVEPOINT، وكل commit للـroute **يفك SAVEPOINT فقط ولا يصدر COMMIT**. ننتظر انتهاء finally/release لكل استدعاء قبل الاستدعاء التالي؛ الالتقاط الأول لرد Express وحده لا يثبت اكتمال تنظيف الاتصال.

1. استهلاك دليل الاختبار وإدخال الطلب وتدقيقه وقراءة/تكرار إيصاله بـSQL الفعلي.
2. مهلة الدعوة/الطلب بقياس DB وقراءة pending/expired الصحيحة، دون تحويل driver لتاريخ الصلاحية.
3. قوائم المالك المحدودة ومؤشر الطالب وDTO معرف/اسم فقط.
4. تغيير اسم السجل بعد المعاينة يرفض409 قبل الربط؛ تُعاد قيم fixture داخل المعاملة.
5. فشل audit محقون، ثم **خطأ ER_DATA_TOO_LONG فعلي من MySQL** في إدخال الإيصال بوضع STRICT. كلاهما يعيد الطالب والطلب والإيصال ورأس التدقيق إلى savepoint الأصلي.
6. تحديث نفس student ID مع حفظ الاسم والهاتف والباركود والملاحظات والصف/المجموعة/الفرع وصفر منح مقررات. ترتيب مفاتيح JSON المختلف يعيد نفس الإيصال. `verifyAuditChain` يثبت السلسلة المرحلية ورأسها.
7. اتصال حقيقي ثانٍ ينتظر قفل المالك، وينتهي بمهلة انتظار1ثانية ورفض مغلق503. هذا **فحص قفل محدود**، وليس سباق موافقتين مع COMMIT أو قياس حمل.
8. ROLLBACK الخارجي يزيل حساب وسجل ودعوة ودليل وطلب وربط وإيصال وتدقيق الاختبار. عادت أعداد users/students/requests/operations/proofs/audits والسلسلة الأصلية كما كانت، وفُحص غياب كل معرف fixture. **صفر صفوف fixture باقية**.

`build53-mysql-results.json`:8نجاحات، فكّا savepoint لنيتي كتابة، وإشارتا إتلاف بعد أخطاء الاختبار، وتوصيل اختبار واحد. enabled:true ومفتاح الاختبار محقونان في المصانع المعزولة فقط؛ لم تُفعّل بيئة الديمو أو قناة إرسال. لا يُقدّم هذا كدليل تحقق هاتف بشري أو auth حقيقي أو حفظ دائم أو استرجاع بعد COMMIT مجهول أو تزامن كتابة إنتاجي.

## ما يلي

تأجيل OTP **قرار مالك**؛ ليس عطلًا يتطلب اختيار مزوّد الآن أو تفعيل قناة وهمية. حين يقرر تشغيله يلزم مزوّد/قناة معتمدان ومفتاح HMAC محفوظ خاصًا، وتوصيل الخدمة الحقيقي ومخطط البيئة المعنية، ثم قبول الهوية والوقت والتزامن والحفظ الدائم والاسترجاع والأجهزة. فتح flag وحده لا يحقق ذلك.

التالي المأذون محليًا **J04: اختبار رحلة الدعم والتكليف/التحويل والمتابعة الفعلية على الديمو ضمن صلاحيات دعم المنصة الحالية**، دون اختراع هوية موظف سنتر أو سياسة SLA أو إرسال خارجي. بقية عقود الأسرة والتصحيح والموسم والوسائط وقياس الفائدة تبقى في القائمة؛ هذه الدفعة لا تعلن انتهاء الخطة أو قبول الإنتاج.
