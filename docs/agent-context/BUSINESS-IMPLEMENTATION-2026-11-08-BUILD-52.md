# BUILD-52 — أولوية ربط حساب الأونلاين بالسجل الموجود

> تحديث BUILD-53: اعتماديات OTP والربط طُبقت لاحقًا على الديمو المعزول فقط، مع اختبار SQL قابل للتراجع وصفر fixture باقية. المالك أجّل SMS/واتساب وربط الأونلاين خلف flag مغلق افتراضيًا؛ غياب المخطط والأولوية التالية أدناه checkpoint تاريخي. [الحالة والقرار الحاليان](BUSINESS-IMPLEMENTATION-2026-11-08-BUILD-53.md).

المالك أجاب صراحة: **«خلّي ربط الأونلاين هو الأولوية»** ثم طلب استكماله. نُفذ مسار مستقل للحساب الموجود: دخول الطالب، تحقق هاتفه، طلب ربط بموافقته، ثم اختيار المالك سجلًا موجودًا ومعاينته وتأكيده. هذه دفعة كود وخادم وواجهة واختبارات، **وليست تفعيلًا فعليًا للتحقق أو قبولًا لإنتاج**.

## تصحيح قرار الأولوية

رد الأولوية وصل بعد تنفيذ BUILD-51، الذي كان قد فسر طلب «كمل» السابق كاستمرار في عرض الأوفلاين. الرد الصريح ليس موافقة على تأجيل الأونلاين؛ هو المرجع الحالي، ويتقدم على ذلك التفسير وعلى أولوية J04 السابقة. إضافات الأوفلاين وبيانات تجربة الديمو السابقة محفوظة، ولا تُلغى أو تُحوّل تلقائيًا. لا يدّعي هذا التقرير موافقة صريحة رجعية عليها. العقد الأصلي M2-16 يبقى استيراد سجلات فقط.

## ما أُضيف في المنتج

- في رابط الانضمام `/join/:token` لوحة «عندك سجل بالفعل عند المدرس؟». يلزم حساب طالب موجود ودخول فعلي؛ غير الداخل يتجه للدخول ثم يعود لرابط المدرس. لا إنشاء حساب آخر أو طالب آخر بهذه اللوحة.
- هاتف الحساب يخضع لمسار OTP الموجود. لا يُقبل الطلب اعتمادًا على `phone_verified` أو قيمة من العميل أو تشابه الهاتف فقط. الحساب الحالي يعاد إثباته من users بالنشاط والتوقيف وإصدار الجلسة، والهاتف يُؤخذ من صفه الحالي على الخادم.
- الطلب يستهلك **دليلًا سبق التحقق منه** لغرض enrollment_join، مرتبطًا بالمؤسسة والهاتف، وبهوية null وفق عقد مسار OTP الأصلي. إعادة استخدامه أو اختلاف الغرض/الجهة/الهوية/الهاتف/الوقت يرفض. `assertConsumed` ومحرك HMAC الحالي معاد استخدامهما؛ استهلاك submitted_at وإدخال الطلب والتدقيق المختوم ضمن معاملة واحدة، فيعود استهلاك الدليل عند فشل الحفظ.
- صلاحية الطلب حتى24 ساعة أو نهاية الدعوة، أيهما أقرب. سحب الدعوة يمنع القبول أو إرسال طلبات جديدة بها؛ الاستعلام التاريخي والسحب الشخصي لا يحولان ذلك إلى صلاحية ربط. عرض الطالب يميز pending/linked/withdrawn/expired؛ لا يُوصف المنتهي بأنه ينتظر المراجعة. يستطيع الطالب سحب الطلب قبل اكتمال الربط، ويمكنه قراءة آخر طلب بعد إعادة التحميل دون إعادة الإرسال.
- لوحة المالك في `/instructor-students` تأتي قبل الأوفلاين. اختيار صريح لطلب وسجل، ثم معاينة تذكر الاسمين وأن الأثر **ربط هوية فقط**، ثم تأكيد المالك أن الحساب والسجل لنفس الطالب. قوائم25عنصرًا بمؤشر UUID وباسميهما ومعرفيهما فقط، بلا جهات اتصال أو رموز.
- النسخة الحالية تستهدف سجلات نشطة مقبولة وداخل فترة القيد، بلا حساب أو مجموعة أو فرع أو أي تعيين مقرر، ومدرسها فارغ أو المالك. يلزم تطابق الهاتف المطبّع بين السجل والحساب، مع دليل تحقق الطالب وطلبه وموافقة المالك؛ التطابق وحده لا يكتب شيئًا. لا تعديل للاسم أو الهاتف أو الصف أو الحالة أو التواريخ أو التاريخ السابق لتجهيز سجل غير مطابق.
- الحفظ يحدّث **نفس student ID** إلى user_id المحدد وis_offline=0 ومدرس المالك، ويحدّث حالة الطلب، ويكتب تدقيقًا مختومًا وإيصالًا في نفس معاملة InnoDB. لا تعيين مجموعة أو مقرر أو دفع أو فك قفل أو إكمال درس. إذا كان للحساب قيد أصلًا بالمؤسسة يرفض؛ لا دمج قيود أو نقل تاريخ.
- فحص فعلي للمخطط والمحركات والمفاتيح الفريدة، بما فيها المفتاح القائم `uq_students_tenant_user(tenant_id,user_id)`، قبل الخدمة. لا نعيد تشغيل migration الأساس القديمة التي تحتوي backfill تلقائيًا.
- الموافقة تكرر إثبات المالك والطلب والدعوة والحساب والسجل والتعيينات والمعاينة الحالية. تغير المصدر يرفض. إعادة نفس العملية والمحتوى تعيد إيصالًا تاريخيًا؛ المحتوى المختلف يرفض. فشل audit/receipt يعيد الربط والطلب وحجز رأس السلسلة؛ COMMIT المجهول يُتلف اتصاله ويعيد PERSISTENCE_UNCERTAIN دون إعادة كتابة تلقائية.
- علامتا جلسة منفصلتان للطالب والمالك، لحساب داخل التبويب، تحتويان المعرفات ونوع العملية فقط. لا هاتف أو اسم أو OTP أو رمز دعوة أو review_token. تُحفظ العلامة قبل POST؛ تعذر حفظها يمنع الإرسال. بعد الانقطاع وإعادة التحميل يكون الاسترجاع GET فقط. السحب عملية منفصلة؛ استعلام pending لا يجوز أن يثبت سحبًا ناجحًا. الحفظ المؤكد يبقى ظاهرًا عند تعذر تنظيف العلامة أو فشل GET لاحق. تغير الجلسة والمهلة والرد المتأخر والتخلص من المكون لها حواجز.

## التالي ضمن أولوية الأونلاين

قبول المخطط والقيود وSQL والتزامن على بيئة الاختبار المحددة، ثم تجهيز قناة OTP معتمدة دون اختراع تسليم أو تعطيل تحقق، ثم تجربة حساب/اتصال فعليين بموافقة المالك. بعد نجاح الربط يأتي إعداد المجموعة/المقرر بإجراء مستقل؛ ما سبق ليس منح وصول. إنشاء حساب أول مرة، ربط قيد له مجموعة/مقررات بالفعل، الدمج بين حسابين، تغيير الهاتف أو تصحيح السجل، وصلاحيات الموظف/الفرع ليست ضمن هذا الربط الابتدائي. باقي J00–J10 ما زال له القياس والعقود والبوابات المسجلة، وJ04 يأتي بعد الأولوية الصريحة الحالية.
